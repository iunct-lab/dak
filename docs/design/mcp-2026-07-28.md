# MCP 2026-07-28 版: DAK への影響と扱い先

PBI #322。MCP 仕様 2026-07-28 の変更点ごとに、DAK のどこに影響し、どこで扱うかをまとめる。
mcp-server の mcp 2.x への移行そのものは `docs/design/mcp_server_upgrade.md`（#39）、
エージェントを 2026-07-28 版でつなぐのは #629。

## 変更点と扱い先

扱い先の「この PBI」は #322 の Task（#324 単体テスト、#325 統合テスト）。

| 変更点（SEP） | DAK の影響箇所 | 扱い先 | 理由 |
|---|---|---|---|
| `initialize` の握手と `Mcp-Session-Id` の廃止、各リクエストの `_meta` に `io.modelcontextprotocol/protocolVersion`・`clientCapabilities`（SEP-2567, SEP-2575） | `mcp-server/main.py`（`MCPServer` と `streamable_http_app()`）、`tests/integration/test_mcp_server.py`（`initialize` と `mcp-session-id` を前提にする） | この PBI | mcp 2.x の `MCPServer` は `_meta` 付きの要求にはセッションなしで、`initialize` で始めた相手には旧仕様のセッションで応じる。両方が同じサーバで通ることを #324・#325 で確かめる。旧仕様のテストは消さない（旧仕様のクライアントもまだ居る） |
| `server/discover`（SEP-2575） | `mcp-server/main.py` | この PBI（#324） | サーバ側は SDK が実装する。DAK のコードは足さない |
| 負荷分散の後ろに置ける（どのインスタンスに送ってもよい） | `mcp-server/main.py`（アプリの組み立て） | この PBI（#324） | 1 つのプロセスで 2 つのアプリを立てて確かめる。実際の複数台の配置はスコープ外 |
| Streamable HTTP の POST の `Mcp-Method`・`Mcp-Name` ヘッダ（SEP-2243） | `tests/integration/test_mcp_modern_client.py`（httpx で直接送る新仕様のクライアント） | この PBI（#325） | SDK の `Client` は自分で付ける。httpx で送るテストは自分で付ける |
| `ttlMs`・`cacheScope`（SEP-2549）、`tools/list` の決まった順 | `mcp-server/main.py`（`tools/list` の応答） | 対応不要 | SDK が応答に付ける。DAK のツール一覧は起動時に固定で、キャッシュの指定を変える理由が無い |
| `subscriptions/listen`（GET の口と `resources/subscribe` の置き換え）、`ping`・`logging/setLevel` の廃止、SSE の再開（`Last-Event-ID`）の廃止 | 無し（DAK の mcp-server はリソースも購読も持たない） | 対応不要 | 使っていない |
| 入力要求の往復 MRTR（`InputRequiredResult`, SEP-2322）、`resultType` | `mcp-server/main.py`（危険操作の確認・支払いの要求を返す口の候補） | #326 | 活用の採否は試作で決める |
| Tasks の拡張 `io.modelcontextprotocol/tasks`（SEP-2663） | `mcp-server/main.py` の `run_command`（長いコマンド） | #326 | 同上 |
| MCP Apps（拡張の枠組みの 1 つ） | `bff/`（HTMX。MCP Apps の UI を iframe で受ける受け皿が無い） | 対応不要 | BFF が MCP の UI を表示する作りではない。受け皿を作るなら別の要望から |
| Roots・Sampling・Logging の非推奨（12 か月以上の猶予, SEP-2577） | mcp-server も agent も使っていない（`grep -rn "sampling\|roots" agent/dak_agent mcp-server/main.py` に当たり無し） | 対応不要 | ツール呼び出しのログは標準エラーの 1 行（`main.py` の `ToolCallLogMiddleware`）で、MCP の Logging ではない |
| 旧 HTTP+SSE の非推奨（1 年の猶予, SEP-2596） | `agent/dak_agent/skill_tools.py::make_mcp_toolset`（`conn_type == "sse"` の分岐）。`agent/dak_agent/agent.py`・`explorer.py`・`remote_tools.py` は Streamable HTTP だけ | 対応不要（今は消さない） | 猶予の間は、SSE しか話さない外部の MCP サーバのために残す。消すなら猶予の終わり（2027-07 ごろ）に別の PBI で |
| 認可: `iss` の検証（RFC 9207, SEP-2468）、`application_type`（SEP-837）、発行元に紐づく資格情報（SEP-2352）、DCR の非推奨 | 無し（DAK の mcp-server は OAuth を持たない。外部サーバへの鍵は `bearer_token_env` の固定の Bearer） | 対応不要 | OAuth を使う口が無い |
| エラー番号の変更（`UnsupportedProtocolVersion` が -32022 など）、リソース未発見が -32602 | 無し（DAK はエラー番号で分岐しない） | 対応不要 | SDK の中で閉じる |
| OpenTelemetry の `_meta` キー（`traceparent` など, SEP-414） | `mcp-server/main.py::_trace_id`（`_meta.traceparent` を読む）、エージェント側は SDK が付ける（`agent/dak_agent/patches.py` の説明） | 対応不要 | 既に `_meta` の `traceparent` を読んでいる |
| `X-DAK-Session-Key` による DAK の利用者セッション | `mcp-server/main.py::_session`、`agent/dak_agent/mcp_headers.py` | #19・#20（既存） | MCP のセッションが無くなっても、利用者セッションはこのヘッダで運ぶ。ヘッダは HTTP のヘッダなので世代に依らない |
| 呼び出し元の MCP を呼び出しごとに渡す | `agent/dak_agent/skill_tools.py`（`caller=True`） | #136（既存） | セッションなしの方が呼び出しごとの接続に向く |

MCP を直接話さない部品: `cli/`（`dak-cli` はエージェントの HTTP の口を呼ぶ。`cli/src/acp_agent.py` はエディタから渡る
MCP サーバを使わない（`new_session` のログ））と `bff/`（エージェントを呼ぶだけ）。どちらも 2026-07-28 版の影響は無い。

## 依存の対応状況（2026-10-26）

| 依存 | DAK の制約（ロック） | 話す仕様 |
|---|---|---|
| mcp（mcp-server） | `mcp>=2.3,<3`（2.3.0） | 2026-07-28 と旧仕様（2025-11-25 まで）の両方。`MCPServer` は要求ごとに世代を見分ける |
| mcp（agent） | `mcp>=2.3,<3`（2.3.0） | 同上 |
| google-adk（agent） | `google-adk[a2a,db,mcp]>=2.12.0,<3`（2.12.0） | 機能フラグ `MCP_MODERN_PROTOCOL`（既定 off）が on なら `server/discover` を先に試し、だめなら `initialize`。off なら `initialize`（旧仕様） |
| mcp 1.x（参考。DAK はもう使わない） | — | 2025-11-25 まで（`SUPPORTED_PROTOCOL_VERSIONS` は 2024-11-05・2025-03-26・2025-06-18・2025-11-25）。最後は 1.30.0。2.0.0 から保守のみ |
| fastmcp（単体パッケージ） | 使っていない | 4.x（4.0.0 から、最新 4.1.4）は mcp SDK v2 の上で 2026-07-28 版と旧仕様の両方に応じる（v4.0.0 のリリースノート）。3.x の対応は未確認。DAK は SDK の `MCPServer` を使う |

- 背景に書いた「google-adk が `mcp<2` で固定」は解けた。google-adk 2.13.0 の `requires_dist` は
  `mcp<3,>=1.24`（`curl -s https://pypi.org/pypi/google-adk/json` の `info.requires_dist`）。
  ADK の Issue #6532 は閉じ、PR #6537 は未マージのまま閉じた（別の変更で入った。どの PR かは未確認）
- DAK のエージェントは `agent/Dockerfile` の `ENV ADK_ENABLE_MCP_MODERN_PROTOCOL=1` で 2026-07-28 版でつなぐ（#629）。
  `0` にすると旧仕様のセッションに戻る。#325 の統合テストはこの `0` の側を旧仕様のエージェントとして使う

## エージェント側の接続（#629）

確認日 2026-10-26。ロックの版は google-adk 2.12.0・mcp 2.3.0（`agent/uv.lock`）。

- 決め方: DAK は自分で世代を選ばず、ADK の MCP 接続（`google/adk/tools/mcp_tool/session_context.py` の `_connect`）に任せる。
  環境変数 `ADK_ENABLE_MCP_MODERN_PROTOCOL=1`（ADK の機能フラグ `MCP_MODERN_PROTOCOL`）なら、まず `server/discover` を送り、
  通れば `initialize` なしの 2026-07-28 版（`Mcp-Session-Id` 無し、各リクエストの `_meta` に `io.modelcontextprotocol/protocolVersion`）でつなぐ。
  サーバが新仕様だと分からなければ（`server/discover` に JSON-RPC のエラーを返す、応答が読めない、新仕様の版を挙げない）、
  `initialize` の握手（旧仕様のセッション）に戻る（mcp 2.3.0 の `mcp/client/_probe.py` の `negotiate_auto`）。
  戻らずにそのまま失敗するのは、通信のエラーと、新仕様だけを話し版が重ならないサーバ（`-32022`）。
  フラグが無いか `0` なら、ADK の既定（2.12.0 では off）に従い、はじめから `initialize` だけを使う
- DAK の既定: `agent/Dockerfile` の `ENV ADK_ENABLE_MCP_MODERN_PROTOCOL=1`。`agent/dak_agent/` の MCP の接続
  （`agent.py`・`skill_tools.py`・`explorer.py`・`remote_tools.py`）はどれも ADK の接続を使うので、この決め方に従う
- 旧仕様に戻す方法: コンテナの環境変数で `ADK_ENABLE_MCP_MODERN_PROTOCOL=0` にする（`docker run -e ADK_ENABLE_MCP_MODERN_PROTOCOL=0 …`、
  compose ならサービスの `environment`。例は `compose/test/mcp-legacy.yml` の `agent-legacy-mcp`）。イメージの作り直しは要らない。
  `0` は「指定なし」と同じ扱いなので、ADK が既定を on に変えたら戻すには `ADK_DISABLE_MCP_MODERN_PROTOCOL=1` が要る
  （`google/adk/features/_feature_registry.py` の `is_feature_enabled`）
- `X-DAK-Session-Key` ヘッダ（`agent/dak_agent/mcp_headers.py` の `session_key_header`）は世代に依らずこれまでどおり送る。
  新仕様では MCP のセッションが無いので、DAK の利用者セッションを運ぶのはこのヘッダだけになる。どのサーバに付けるかは
  `docs/design/session-sandbox.md`（#696）のまま変わらない
- 確かめたテスト:
  - `agent/tests/test_mcp_modern_protocol.py`（#631）: 新仕様のサーバに `initialize` なしで `tools/call` が通り `Mcp-Session-Id` が付かない（`-k modern`）、
    旧仕様のサーバには `server/discover` → `initialize` → `tools/call` の順で戻って通る（`-k legacy`）
  - `tests/integration/test_skill_flow.py::test_agent_uses_modern_mcp_protocol`（#212）: 統合構成のエージェントのフラグが `1` で、
    同じファイルの `enable_skill` → `read_file` が mcp 2.x の mcp-server を相手に `Session terminated` にならずに通る

## 見張り方

- 定期の `feature-sync.yml` と Dependabot は #822 でやめた（`docs/maintenance/README.md`）。今の `dak-maint feature-sync` は
  マージ済みの `deps` の PR の本文にある Dependabot 形式の行（`Updates <pkg> from … to …` か `Bumps …`）から更新を拾うので、
  手で書いた PR にその行が無ければ拾わない。依存を上げない限り mcp・google-adk の新しい版には気づかない
- 見張る点は 2 つ: (1) google-adk の `MCP_MODERN_PROTOCOL` が既定 on になるか（なったら Dockerfile の `ENV` は不要）、
  (2) mcp 3.x と google-adk の `mcp<3`。依存を上げる作業（`deps:` の Task）のときに、上の `curl` と
  `google/adk/features/_feature_registry.py` の `_MCP_MODERN_PROTOCOL` の `default_on` を見る。
  仕組みとして足す（定期の確認を戻す）かは #822 の判断の範囲で、この PBI では足さない

## 確かめた結果

- #324（`mcp-server/tests/test_modern_protocol.py`）: mcp 2.3 の `Client(mode="2026-07-28")`（旧仕様に切り替えない固定）で、
  `initialize` なしに `server/discover` → `tools/list` → `tools/call read_file` が通り、どの応答にも `Mcp-Session-Id` が無い。
  `main.create_app()` で立てた 2 つのアプリの 1 つ目で一覧、2 つ目で呼び出しを送っても通る
  - そのために `main.py` は `create_app()` が `MCPServer` をアプリごとに作る形にした。SDK のセッション管理はサーバごとに 1 つで、
    その `run()` は 1 回しか始められないので、1 つの `MCPServer` を 2 つのアプリで共有すると 2 つ目の起動が失敗する
  - SDK の `Client` は、一覧を取っていないツールを呼んだ後に `tools/list` を取り直すことがある（2 つ目のアプリへの要求は
    `tools/call` が先）。サーバ側の扱いではない

- #325（`tests/integration/test_mcp_modern_client.py`、`compose/test/mcp-legacy.yml`）: 統合構成（fake-LLM）の同じ mcp-server に、
  `ADK_ENABLE_MCP_MODERN_PROTOCOL=0` のエージェント `agent-legacy-mcp`（ログは `MCP connected: protocol=2025-11-25`）の 1 ターン目
  （`enable_skill` → `read_file`）で開いた旧仕様のセッションが開いている間に、httpx で送る 2026-07-28 版の `tools/call read_file`
  が通り、その後の 2 ターン目（同じ ADK のセッション）の `read_file` も、つなぎ直さずに（`MCP connected` の行が増えずに）同じ
  セッションで通る。ADK はヘッダごとに MCP のセッションを保持して使い回すため。ADK がこれをやめると、この確認は落ちる。
  既定のエージェント（`agent`）は同じ実行で `protocol=2026-07-28` でつないでいた。
  - 新仕様の POST は `Mcp-Name` が要る。`tools/call` に付けないと mcp-server は 400（`-32020`、「mcp-name header does not match」）を返す
  - 旧仕様のテスト（`test_mcp_server.py` の `initialize` と `mcp-session-id`）も同じ実行で pass。統合テスト全体は 110 passed / 18 skipped
